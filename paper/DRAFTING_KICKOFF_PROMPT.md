## Phase 0 — reconcile before drafting (do this yourself, main thread, do not delegate)

This is the highest-leverage 30 minutes of this whole session. Drafting
on top of unreconciled context docs produces a paper that looks done and
is not.

1. **Resolve, or explicitly flag as unresolved, the exchange-cadence
   discrepancy.** `methodology_facts.md` already documents this: the
   delivered DGX data (100,800 rows/condition over 30 days, 140 agents)
   implies roughly 24 exchanges per agent per day, not the "one exchange
   per agent per day" that `src/simulation.py` and the current
   `DRAFT.md` describe. Do not write the paper's Methods section
   describing the loop as "once per day" until this is confirmed. If
   Rossetti's actual DGX loop code/diff is not available in this
   session, draft Methods with the cadence described honestly as
   "approximately 24 exchanges per agent per day, per the delivered
   data's row structure; exact loop mechanics pending confirmation from
   the collaborator who ran it" rather than picking one description and
   hoping it is right. This is a wording choice, not a blocker — do not
   stall the whole draft on it, but do not paper over it either.

2. **Update `paper/context/hypothesis_and_scope.md` with the actual
   outcome.** The pre-registered hypothesis was: theory-of-mind memory
   reduces unconditional agreement more than factual memory alone, and
   combined memory produces the most stable opinions. The actual
   4-condition results (see `reports/plain_language_summary.pdf`) show
   close to the reverse for the "most stable" claim: combined memory
   (Full KG) produces the **most** fragmented, least stable population,
   not the most stable, while `general_only` (facts alone) produces the
   strongest convergence. Append an "Outcome" section to
   `hypothesis_and_scope.md` stating this plainly: what was predicted,
   what was found, and that the finding is a reversal on the stability
   axis specifically, not a confirmation. The paper should report this
   as a real, interesting negative/reversed result — that is a
   legitimate and often stronger contribution than a confirmed
   prediction, not a failure to hide. Do not let Results or Discussion
   quietly restate "Information Paradox" / "Memory Asymmetry Principle"
   as if they were the original hypothesis.

3. **Decide how to handle the external results report's numbers.**
   `reports/plain_language_summary.pdf` is grounded in an HTML file
   ("Opinion Dynamics — Research Report") that was reviewed but is not
   itself part of this repository, and its richer analyses (sentiment
   via distilbert, fallacy detection via an ELECTRA classifier,
   conceptual-core Jaccard analysis, 19 statistical null models) are
   not reproducible from any code currently in this repo. Two things to
   do here, not one:
   - Confirm with Rossetti (or from whatever channel that HTML report
     arrived through) whether it represents his own analysis of the
     same DGX-delivered dataset this repo already has, or a separate
     pipeline. If it is his, the paper's Methods section needs a
     sentence or two describing those additional analyses (sentiment
     classifier, fallacy classifier, conceptual-core computation) even
     though the code for them is not in this repo — ask him whether
     that code can be shared/merged, since a reviewer will eventually
     ask "how was sentiment measured" and "code available" is a
     standard expectation.
   - Regardless of the answer, copy the specific numbers this paper
     will actually cite out of the PDF and into a new, in-repo file —
     for example `reports/full_ablation_summary.md` — with each number
     labeled by which condition, which metric, and whether it is
     reproducible from this repo's own `analysis/` code or supplied
     externally. This is what `paper-writer` should be pointed at for
     the Results section, not the external HTML file or a PDF outside
     `reports/`, per its own grounding rules.
   - While copying these numbers over, also fix the one concrete
     inconsistency already found: `reports/plain_language_summary.pdf`
     Caveat 2 documents that the external report's own headline
     sentence ("Full KG produces half the fallacy rate of No Memory,
     38.9% vs 83.7%") mixes two different fallacy metrics; the
     self-consistent numbers are 38.9% vs 61.1% on the same metric. Use
     the self-consistent numbers. Spend a little time spot-checking a
     handful of the external report's other charts/tables for the same
     kind of mismatch before trusting them wholesale — Caveat 2 found
     one example, not a guarantee there are no others.

4. **Confirm (or explicitly flag as still open) the target venue and
   LaTeX class.** `style_guide.md` assumes EPJ Data Science / `sn-jnl`
   as the natural default (direct extension of Cau et al. 2025, same
   venue) but says this is unconfirmed. Draft in plain `article` class
   per the style guide's own contingency plan, and add "confirm venue
   and LaTeX class with Rossetti" to the list of open questions this
   session surfaces at the end (see "What to report back," below). Do
   not silently assume `sn-jnl` and format for it without confirmation.

5. **Run citation sourcing** (invoke the `citation-sourcing` skill) on
   all five "needs sourcing" entries in `related_work_sources.md`
   before Related Work is drafted:
   - FSRS (Free Spaced Repetition Scheduler) — check what GhostKG's own
     documentation/README cites as the source algorithm first.
   - GhostKG itself — ask Rossetti directly whether it has its own
     paper/technical report (flag as an open question if this session
     cannot reach him).
   - LLM sycophancy / agreement bias in single-turn, single-agent
     settings.
   - Classical opinion dynamics models (DeGroot, bounded confidence /
     Hegselmann-Krause, voter models) as precedent for the entropy and
     transition-matrix metrics used here.
   - LLM agent memory architectures generally (RAG, agent memory
     systems), to place GhostKG's decaying dimension-typed graph in
     context.
   Use a real literature-search tool for each (a paper-search or
   deep-research skill if this session has one, or a direct OpenAlex/
   PubMed/web search) — do not generate a candidate citation from model
   memory and do not move anything into "Confirmed" without an actually
   resolved DOI or URL.

## Phase 1 — dispatch section writers

Once Phase 0 is complete (grounding docs reconciled, citations sourced,
venue decided-or-flagged, in-repo results file exists), split section
work as follows.

**Independent — dispatch as parallel subagent calls in one message**
(each a `paper-writer` agent call with the section name and the
relevant grounding docs):
- Related Work (now that Confirmed citations exist)
- Methodology (from `methodology_facts.md`, cadence caveat included)
- Limitations (from `hypothesis_and_scope.md`'s scope section)

**Sequential — each needs the previous drafted first:**
1. Experiments (needs Methodology settled)
2. Results (needs `reports/full_ablation_summary.md` from Phase 0)
3. Discussion (needs Results drafted, must reference its actual claims)
4. Conclusion (needs Discussion drafted)

**Revision, not from-scratch:** Abstract and Introduction already exist
in full in `DRAFT.md` but describe the old 10-day baseline and the
original (now partially reversed) hypothesis framing. Revise them after
Discussion and Conclusion are drafted, so the headline claims in the
opening match what the paper actually ends up arguing — do not draft
these two first and then leave them stale a second time.

If this session has been given multi-agent orchestration (the user said
"use a workflow" or ultracode is on), you may use the Workflow tool to
run the independent-section group in parallel with per-section
verification. Otherwise, dispatch the independent group as three
parallel `Agent` tool calls in a single message (they run in the
background; you'll be notified as each completes) and run the
sequential group as ordinary sequential `Agent` calls.

**Model notes:**
- Section drafting (`paper-writer`): Sonnet-class is sufficient and is
  already the agent's configured default — the discipline comes from
  the grounding docs and refusal rules, not raw model capability.
- Citation verification (`citation-sourcing`): use a model with real
  web-search tool access; prefer Opus-class for this one narrow task if
  available, since the cost of a wrong resolved-but-mismatched citation
  is high and this step benefits from careful, skeptical checking more
  than from generation quality.
- Phase 2 integration/coherence read (below): Opus-class if available —
  this is a long-context, whole-document consistency judgment task
  (does Discussion actually follow from Results, does any claim drift
  from the grounding docs), which benefits more from careful reasoning
  across the whole draft than from prose generation.

## Phase 2 — integrate and review (main thread, not a subagent)

1. Assemble the six drafted sections plus the revised Abstract/
   Introduction into `paper/DRAFT.md` (or split into per-section files
   under `paper/latex/` once converted, `\input{}`-linked from a main
   `.tex` file — cleaner for Overleaf review than one giant file).
2. Read the whole draft straight through. Specifically check: does any
   Discussion or Conclusion claim outrun what Results actually
   supports; does every citation in prose appear in the Confirmed tier;
   does any Methodology claim drift from `methodology_facts.md`.
3. Run an AI-writing-pattern cleanup pass (the `avoid-ai-writing` skill,
   per `style_guide.md`'s own instruction) before treating any section
   as finished.
4. **Stop here for human review.** Do not push to Overleaf or message
   Rossetti until Pranav has read the draft. Summarize what was drafted,
   what open questions remain (venue confirmation, GhostKG citation,
   the exchange-cadence diff, the external report's provenance), and
   wait.
5. Only after that review: convert to LaTeX (per `style_guide.md`,
   `article` class unless venue was confirmed as `sn-jnl` in Phase 0),
   place it under `paper/latex/`, and use the `overleaf-sync` skill to
   push. Overleaf project creation itself is a manual step for Pranav
   (or Rossetti, if he already made one) — the skill documents exactly
   what to do and what to hand back to this session (the git clone URL)
   once that exists.
